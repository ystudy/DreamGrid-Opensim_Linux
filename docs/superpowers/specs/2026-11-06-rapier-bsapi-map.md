# Rapier behind BulletSim's engine interface: method map (feasibility Phase 1.2)

**Question:** can a third `BSAPITemplate` backend (`BulletEngine=Rapier`) that maps BulletS's engine calls
onto Rapier's C API be the prototype route? Or should the prototype be a new physics module written from
scratch?

**Status:** desk check, reading only. Written 2026-11-06 for
`docs/superpowers/plans/2026-11-06-rapier-feasibility.md`, Phase 1.2.

**Short answer:** yes, the backend route works for a prototype. Of the 102 methods BulletS calls, 36 map
directly, 64 are emulated (15 of those are no-ops), and 2 are gaps. Both gaps are sleep-tuning knobs that can
be ignored. Nothing needs a change inside Rapier. The shim is about 2,500 to 3,500 lines of C#, roughly the size
of `BSAPIXNA.cs`. P/Invoke straight into `rapier.h` is enough, with no Rust shim needed to start.

## Sources and method

- **OpenSim side:** `OpenSim/Region/PhysicsModules/BulletS/` in this repo. That's `BSApiTemplate.cs`, the two
  existing backends (`BSAPIUnman.cs`, P/Invoke to native BulletSim; `BSAPIXNA.cs`, managed), and every caller.
- **Rapier side:** `rapier.h` from rapier 0.36.1's C bindings (`bindings/c`, 21,871 lines, generated by
  cbindgen), plus `bindings/c/README.md` and the official C# example `bindings/c/examples/RapierNative.cs`.
  - The header declares **739 distinct `r3*` names** (the plan's "about 300" was low). They include soft
    bodies, FEM and robotics.
  - The joint API is broader than the plan says. Besides fixed and revolute joints there are generic 6-axis
    joints (per-axis locks, limits, motors and softness), spherical, prismatic, rope, spring and pin-slot
    joints. There is also a ray-cast vehicle controller and a PID controller.
- **Native BulletSim C++** (github.com/Misterblue/BulletSim: `BulletSim.cpp`, `BulletSim.h`, `API2.cpp`,
  `APIData.h`). Read to confirm what the native side does with the flags and the step arrays.
- **How "BulletS calls it" was found:** grep of `.<Method>(` over every BulletS `.cs` file except the three
  API files, with commented-out lines removed, then a reading of each call site.
  - **yes:** called on a normal path.
  - **rarely:** only from debug output, a parameter-change setter, or a non-default configuration. The
    configuration is named in the Caller column.
  - **never:** no live call.
- **Every `r3*` name in the table** was checked by script against the function list extracted from
  `rapier.h`. All of them exist. Signatures were read for the ones the hard parts depend on.
- **Method count:** `BSAPITemplate` has **176 abstract members** (174 methods and 2 properties) plus **8
  virtual debug/reset methods** with empty defaults. That's **184** in all, not the 180 the plan quotes. All
  184 are listed.

**Mapping legend:**

- **direct:** one or a few named `r3*` calls, plus C# marshalling.
- **emulate:** done in the C# backend, by keeping state C#-side, combining calls, or translating Bullet's
  convention. A sentence says how.
- **emulate (no-op):** the call is a Bullet implementation detail with nothing to do in Rapier. It is
  counted under emulate.
- **gap:** Rapier's C API has nothing to map it to.

## 2. The hard parts

Each part says what Bullet and BulletS do, what Rapier has, and the proposed approach. File and line references
are to this repo unless they name BulletSim's C++.

### H1. The bulk "updated entities" array (motion states)

- **Bullet:** BulletSim's C++ `SimMotionState::setWorldTransform` (`BulletSim.h`) runs for every moving body
  on every substep.
  - It adds the body to `updatesThisFrame` when position, rotation or velocities moved more than fixed
    tolerances, or when both velocities have just become zero.
  - `PhysicsStep2` (`BulletSim.cpp`) copies that map into the shared EntityProperties array, up to
    `MaxUpdatesPerFrame` (8,000 by default). BSScene then calls `UpdateProperties` on each object.
  - With `BS_RETURN_ROOT_COMPOUND_SHAPE`, the pose reported is that of compound child 0.
- **Rapier:** there are no motion states. Two bulk calls cover it:
  - `r3ActiveRigidBodies(world, buffer, capacity)` copies the handles of the awake bodies.
  - `r3RigidBodyReadStates(world, handles, n, states, capacity)` copies pose, linvel, angvel, sleeping and
    userData for a list of handles.
- **Approach:** after the last substep, PhysicsStep makes those two calls. C# then does the rest:
  - It compares each state with the last EntityProperties it sent, using BulletSim's tolerances.
  - It adds one final zero-velocity update for bodies that dropped out of the active set (fell asleep). This
    is the behaviour BulletSim gets from its Bullet patch.
  - It adds the bodies queued by `PushUpdate`.
  - For `BS_RETURN_ROOT_COMPOUND_SHAPE` it multiplies in child 0's local pose. BulletS only sets that flag
    with `UseBulletSimRootOffsetHack`.
  - The localID is in the body's userData.

  This is two P/Invokes per frame plus C# work proportional to the number of moving bodies, which is no worse
  than today.

### H2. The bulk "collisions" array

- **Bullet:** BulletSim registers `SubstepCollisionCallback` (`BulletSim.cpp`), so collisions are gathered
  after every substep. It walks every contact manifold that has points. `RecordCollision` keeps a pair only
  when one side has `BS_WANTS_COLLISIONS`, which is `BS_SUBSCRIBE_COLLISION_EVENTS | BS_VEHICLE_COLLISIONS`
  (`0x1400`, `APIData.h`).
  - Each pair is stored once per frame as low ID, high ID, one point, one normal and the penetration.
  - Ghost objects add pairs from their pair cache (contacts with distance < 0).
  - BSScene sends every pair in both directions. The cap is 2,048 per frame (`MaxCollisionsPerFrame`).
- **Rapier:** the matching calls all exist:
  - `r3Collider_ContactPairs(collider, ...)` lists the narrow-phase pairs that involve one collider. Each
    R3ContactPair carries `has_any_active_contact` and impulse totals.
  - `r3ContactPoints(c1, c2, ...)` returns points (collider-local), the world normal, distance and impulse.
  - `r3IntersectionPairs` lists sensor overlaps.
  - The event collector (`r3EventCollector_CollisionEvents`) only reports start and stop. BulletS wants every
    frame of contact, so it polls pairs rather than using events.
- **Approach:** the backend keeps a "wants collisions" set of colliders, fed by the flags (H3). Those colliders
  also get `R3_COLLISION_EVENTS`, and every `r3Step` is given the world's event collector.
  1. After each substep, read the collector (one call when it is empty) and clear it. A contact that started is
     written then, from `r3ContactPair` and its deepest point. A pair that stopped in any substep but the first
     was still touching after the one before, so it is written with the entry it had last frame.
  2. After the last substep, one `r3ContactPairs` call lists every pair in the world, each once. For each pair
     not yet seen this frame that has an active contact and a collider in the set, call `r3ContactPoints`. Take
     the deepest point, convert it to world space with the collider pose, and write a CollisionDesc.

  Sensors come from one `r3IntersectionPairs` call. Their point is the other body's position and their
  penetration is 0. Scripts only need the detected object for volume detect.
  - **Cost:** one pair-list call per frame, one event read per substep, plus two calls per reported pair. The
    first version called `r3Collider_ContactPairs` per subscribed collider per substep, which cost 3.9-4.3 ms
    per frame in busy scenes (perf investigation, 2026-11-06).
  - **If the calls show up in profiles:** a small Rust shim can return all CollisionDescs in one call
    (Phase 1.3).
  - **Brief touches:** gathering only after the last substep would miss them, so the events cover the
    substeps in between. BulletS's avatar code uses `CollisionsLastTick`.

### H3. Collision flags, activation states, body types and filter groups

**Collision flags** are kept C#-side, and each one becomes a Rapier setting:

| Flag | BulletS use | Rapier |
| --- | --- | --- |
| `CF_STATIC_OBJECT` | Static prims and terrain. BulletS keeps the same body and toggles mass 0 + flag (`BSPrim.MakeDynamic`). | `r3RigidBody_SetBodyType(R3_FIXED)` or `R3_DYNAMIC`, in place; the handle survives. |
| `CF_KINEMATIC_OBJECT` | Never set by BulletS (grep). | `R3_KINEMATIC_POSITION_BASED` if ever needed. |
| `CF_NO_CONTACT_RESPONSE` | Non-solid prims (`BSPrim.MakeSolid`) and linkset children hidden inside the root's compound (`BSLinksetCompound`). | `r3Collider_SetSolverGroups` with filter 0. Contacts are still computed (so collisions are reported) but produce no forces: the header describes solverGroups as the groups "controlling contact-force solving". |
| `CF_CHARACTER_OBJECT` | Avatars, as a marker. | Nothing. |
| `CF_CUSTOM_MATERIAL_CALLBACK` | Terrain mesh. | Build that trimesh with `R3_TRIMESH_FIX_INTERNAL_EDGES`. (What BulletSim's callback does wasn't checked.) |
| `BS_SUBSCRIBE_COLLISION_EVENTS`, `BS_VEHICLE_COLLISIONS` | Objects with collision scripts, avatars, vehicles. | The wants-collisions set (H2). |
| `BS_FLOATS_ON_WATER` | Set by BSPrim and BSCharacter. | Nothing. The native code defines it (`APIData.h`) but never reads it: it doesn't appear in `BulletSim.cpp`, `BulletSim.h` or `API2.cpp`. Buoyancy is done in C# through gravity (H6). |
| `BS_RETURN_ROOT_COMPOUND_SHAPE` | Linkset root offset hack. | In PhysicsStep (H1). |

**Activation states** (`ForceActivationState`):

- **`ACTIVE_TAG`:** `r3RigidBody_WakeUp`.
- **`ISLAND_SLEEPING`:** `r3RigidBody_Sleep`.
- **`DISABLE_DEACTIVATION`:** used for avatars (`BSCharacter.cs:182`) and some prims (`BSPrim.cs:1016`).
  Rapier's `canSleep` exists only in R3RigidBodyDesc at creation; rapier.h has no setter. So the backend keeps
  a never-sleep set and wakes it before each step. That costs one call per avatar, or the body could be
  recreated with canSleep 0.
- **`DISABLE_SIMULATION`:** on terrain and the ground plane it is a no-op, because fixed bodies don't simulate
  but still collide. On hidden linkset children it becomes `r3RigidBody_SetEnabled(0)`.

**Sleep thresholds and deactivation time** are the only gaps BulletS actually calls. Rapier's C API exposes no
sleep tuning, so its defaults apply. This is a tuning difference, not a blocker.

**Filter groups:**

- BulletS gives every CollisionType a group and a mask (`BulletSimData.CollisionTypeMasks`) and applies them
  with `SetCollisionGroupMask` after each `AddObjectToWorld`.
- Bullet's broadphase rule is `(a.group & b.mask) && (b.group & a.mask)` (stock Bullet; BulletSim's build
  unverified).
- Rapier's R3InteractionGroups is `{memberships, filter, test_mode}`, where test_mode 0 "requires both
  membership/filter tests". That is the same rule.
- The masks fit in 32 bits. Ray casts pass the same pair through `R3QueryFilter.groups` with `use_groups = 1`.
- **Body-type pairs:** Rapier's `R3_COLLISION_TYPES_DEFAULT` (15) covers dynamic-dynamic, dynamic-fixed and
  dynamic-kinematic. Fixed-fixed contacts are skipped, as in Bullet. Sensors get wider types (H4).

### H4. Ghost objects: volume detect and phantom

- **BulletS:** a non-solid prim gets `CreateGhostFromShape` (a `btPairCachingGhostObject`) plus
  `CF_NO_CONTACT_RESPONSE` and CollisionType.VolumeDetect (`BSShapeCollection.CreateBody`,
  `BSPrim.MakeSolid`).
  - Plain phantom prims never reach physics: SceneObjectPart removes them (comment at `BSPrim.IsPhantom`, `BSPrim.cs:1108`).
    So "phantom" only matters as phantom + volume detect.
- **Rapier:** a sensor collider (`isSensor = 1` in R3ColliderDesc, or `r3Collider_SetSensor`) on a fixed or
  kinematic body. Overlaps come from `r3IntersectionPairs`, or from collision events with
  `R3_COLLISION_EVENT_SENSOR`.
  - **Approach:** set `activeCollisionTypes` on sensor colliders to include
    `R3_COLLISION_TYPES_KINEMATIC_FIXED` and `R3_COLLISION_TYPES_FIXED_FIXED`, so a static volume-detect prim
    also sees kinematic and static things. Report overlaps as in H2.
  - There is no contact point, so a stand-in is used (H2).

### H5. Compound shapes, linksets and 6-DOF (spring) constraints

**Linksets as compounds** (the default; `LinksetImplementation` is 1, compound, at `BSParam.cs:831`).
`BSLinksetCompound.RecomputeLinksetCompound` does the following:

- Builds a compound with one `AddChildShapeToCompoundShape` per member, offset from the centre of mass.
- Takes the children out of play with `CF_NO_CONTACT_RESPONSE` + `DISABLE_SIMULATION`, and unsubscribes them.
- Swaps the root's shape with Remove / `SetCollisionShape` / Add.
- Later moves single children with `UpdateChildTransform`. A child shape can itself be a compound: a
  multi-hull `BSShapeHull`.

Rapier offers two ways to do this:

- **(a) `r3CompoundSharedShape`:** immutable, so it is rebuilt on every change. Parry (Rapier's geometry
  library) doesn't allow composite shapes inside a compound (from Parry's documentation, not checked in
  rapier.h). Nested hull compounds would have to be flattened, and trimesh children couldn't be used at all.
- **(b), proposed: one Rapier collider per child shape, all attached to the root body.** Use `r3InsertCollider`
  with the root as parent and the child pose in `R3ColliderDesc.position`, which is relative to the parent.
  - This flattens nested compounds and allows trimesh children.
  - `UpdateChildTransform` becomes one `r3Collider_SetPositionWrtParent`.
  - Every collider's userData holds the root's localID. Bullet reports compound contacts under the root's ID
    because the compound has one user pointer, and BulletS expects that.
  - Mass: colliders get density 0, and BulletS's own linkset mass and inertia go in
    `r3RigidBody_SetAdditionalMassProperties`.

**Constraint linksets and axis locks:**

- `BSLinksetConstraints` (non-default) and `BSActorLockAxis` (axis locks) use Bullet's 6-DOF constraint.
- Rapier's generic joint (`r3DefaultJointDesc`, `R3JointDesc` with `lockedAxes`, `limitAxes`, `motorAxes`
  and six `limits[]` and `motors[]`) covers it. Translate Bullet's per-axis convention: lo == hi locked,
  lo < hi limited, lo > hi free.
- A joint to "the world" needs one shim-owned fixed body, because Rapier joints always join two bodies.
- **Breaking thresholds:** read `r3ImpulseJoint_Impulses` after the step.
- **ERP/CFM:** only approximate, through `r3ImpulseJoint_SetSoftness` (natural frequency and damping ratio).

**6-DOF springs** (`BSConstraintSpring`, used by ExtendedPhysics spring links):

- Bullet's btGeneric6DofSpringConstraint has a spring per axis with an equilibrium point, stiffness and
  damping.
- Rapier's per-axis joint motor (R3JointMotor: `targetPos`, `targetVel`, `stiffness`, `damping`, `maxForce`,
  `model`) is a spring-damper toward targetPos. Use `model = 1` (force-based) so stiffness is a force per
  metre, as in Bullet. Whether the two behave the same is unverified; it is a tuning item.
- **Calls:** `r3ImpulseJoint_SetMotor`, `r3ImpulseJoint_SetMotorPosition`, `r3ImpulseJoint_SetMotorModel`.

**Never instantiated:** hinge, slider and cone-twist (their BS classes exist but nothing creates them). Gear
is never called. Of these, only gear (no two-body ratio joint) and the slider softness settings are gaps, and
neither is used.

### H6. Per-body gravity

- **Bullet:** gravity is a vector per body.
- **Rapier:** only a scalar `gravityScale` per body (`r3RigidBody_SetGravityScale`).
- **What BulletS passes:** only vectors parallel to world gravity.
  - Buoyancy and gravity modifier: `BSPrim.ComputeGravity` = DefaultGravity × (1 − buoyancy) × GravModifier.
  - Avatar buoyancy and flying: `BSCharacter.ForceBuoyancy` = (0, 0, Gravity × (1 − buoyancy)).
  - Vehicles and linksets reuse ComputeGravity.

  So `gravityScale = g.Z / worldGravity.Z` is exact. If another vector ever arrives, the backend adds
  `mass × (g − scale × worldG)` with `r3RigidBody_AddForce` each step.

### H7. CCD (swept sphere)

- **Bullet:** CCD per body from a motion threshold plus a swept-sphere radius.
- **BulletS:** sets these only when `CcdMotionThreshold > 0`. The default is 0, so CCD is off
  (`BSParam.cs:586`).
- **Rapier:** CCD per body (`r3RigidBody_SetCcdEnabled`), with world limits (`r3SetMaxCcdSubsteps`,
  `r3SetMinCcdDt`) and an optional soft-CCD prediction distance (`r3RigidBody_SetSoftCcdPrediction`). Rapier
  sweeps the real shape rather than a sphere.
- **Approach:** `threshold > 0` turns CCD on; the radius is ignored or fed to soft CCD.
- **Benefit:** Rapier's CCD is a likely gain for fast objects (bullets, vehicles), but it is unverified.

### H8. Heightfield terrain and varregion sizes

- **BulletS:** uses the heightmap terrain by default (`TerrainImplementation` default 0, `BSParam.cs:602`).
  `CreateTerrainShape2` (`API2.cpp`) builds `btHeightfieldTerrainShape(sizeX, sizeY, heightMap, 1, minZ,
  maxZ, upAxis = 2 (Z), PHY_FLOAT)` with diamond subdivision. BSTerrainHeightmap places the body at the map's
  centre in X and Y and at `(minZ + maxZ) / 2` in Z (`BSTerrainHeightmap.cs:99-103`), because Bullet centres
  the field between min and max.
- **Rapier:** `r3HeightfieldSharedShape(heights, rows, columns, scale)` copies the samples (column-major,
  `rows × columns`). `R3_HEIGHTFIELD_FIX_INTERNAL_EDGES` is available through `R3ShapeDesc.flags`. From Parry's
  documentation, not checked in rapier.h: Rapier's heightfield is Y-up, centred in X and Z, and its heights are
  absolute (× scale.y), not centred.
- **Approach:**
  1. Copy the C# heightmap (row-major, X fastest) into column-major order.
  2. Rotate the collider +90 degrees about X so Rapier's Y becomes world Z. This also flips Rapier's Z into
     world −Y, so flip the row order.
  3. Undo Bullet's vertical centring with a Z offset. The backend knows minZ and maxZ from the
     CreateTerrainShape arguments.
  4. Choose the X/Z scale so the sample spacing is 1 m. Whether Bullet's grid spans sizeX or sizeX − 1 metres
     needs checking.

  Check all of this with ray casts at the corners and the centre in Phase 3. Getting the orientation wrong is
  the most likely early bug.
- **Triangle split:** Bullet's diamond split and Rapier's split (which way is unverified) can put the surface
  between samples a few centimetres apart. `BSTerrainHeightmap.GetTerrainHeightAtXYZ` interpolates in C#, so
  ground height and the collision surface may disagree slightly. That is the same kind of mismatch as today.
- **Varregions:** the heightmap is the region's size, so any size works. Rapier keeps its own copy (the
  header says "copied samples"). A 4,096 × 4,096 region is 16.7 M floats, about 67 MB more. A 256 or 512
  region is negligible.
- **Mesh terrain:** `TerrainImplementation = 1` maps directly to a trimesh.

### H9. Convex hulls from meshes, HACD, and shape scaling

**How BulletS picks a shape** (BSShapes): static prims and meshes become trimeshes (`CreateMeshShape`).
Physical ones become one of:

- hulls from the mesh asset (`CreateHullShape`);
- a single convex hull of the mesh (`BuildConvexHullShapeFromMesh`, default `ShouldUseSingleConvexHullForPrims
  = true`);
- Bullet's HACD (`BuildHullShapeFromMesh`, only with `ShouldUseBulletHACD`, default false);
- or hulls from BulletS's C# code (`CreateHullShape`).

**Rapier:**

- `r3ConvexHullSharedShape` computes a hull.
- `r3ConvexMeshSharedShape` takes an already-convex mesh.
- `r3ConvexDecompositionSharedShape` decomposes a mesh. It takes no parameters, so `HACDParams` are dropped.
  BSAPIXNA already forces `ShouldUseBulletHACD` off, which is a precedent (`BSScene.cs:459-462`).
- `r3CompoundSharedShape` joins shapes.
- `r3TrimeshSharedShapeWithFlags` builds trimeshes.

All the routes BulletS uses map directly.

**Scaling:**

- BulletSim's `BuildNativeShape2` builds unit shapes (box half-extent 0.5, sphere radius 0.5, and so on) and
  calls `setLocalScaling`.
- BSCharacter calls `SetLocalScaling` when an avatar's size changes.
- Rapier's shared shapes are immutable ("sharing the same immutable geometry", `r3SharedShape_Clone`). The
  backend builds native shapes at their final size, and on SetLocalScaling builds a new shape and calls
  `r3Collider_SetShape`.
- Meshes and hulls come from BulletS already scaled.

**Margins:** Bullet's convex margins (`collisionMargin`) don't exist in Rapier. Objects will rest a few
centimetres differently. This is tuning.

### H10. The avatar: BulletS's movement against Rapier's character controller

- **BulletS's avatar is a dynamic rigid body**, not a kinematic controller.
  - **Shape:** a box by default (`AvatarShape` default 1 = `AvatarShapeCube`, `BSParam.cs:634-635`); a
    capsule is optional.
  - **Rotation** is locked with `SetAngularFactorV(0)` (`BSCharacter.cs:172`).
  - **Never sleeps:** `DISABLE_DEACTIVATION`.
  - **Movement:** `BSActorAvatarMove` runs a velocity motor each pre-step and pushes the body with
    `ApplyCentralImpulse` (`BSActorAvatarMove.cs:309`).
  - **Friction** switches between standing and moving (`:229`, `:264`).
  - **Stairs:** `WalkUpStairs` (`:329-420`) adds an upward impulse worked out from the contact points in
    `CollisionsLastTick`.
  - **Flying** is reduced gravity (H6).
- **On the template route, all of that maps directly:** a dynamic body with locked rotations
  (`r3RigidBody_SetLockedAxes`), impulses, per-collider friction, and the contact points from H2. Rapier's
  `KinematicCharacterController` (`r3NewKinematicCharacterController`, `_MoveShape`, `_SetAutostep`,
  `_SetSlopes`, `_SetSnapToGround`, `_SetUp`) isn't needed and isn't used.
- **Consequence:** avatars will walk like BulletSim avatars, not ubODE ones. The step logic depends on contact
  heights and normals, and those shift with Rapier's lack of margins. Expect to retune the `AvatarStep*`
  parameters.
- **If Phase 4 stairs and slopes fail:** a new BSActor that uses Rapier's controller with a kinematic avatar
  body could replace `BSActorAvatarMove`. That is C# inside BulletS, outside the template. A few hundred lines
  (unverified estimate).

### H11. Materials, damping, forces and factors

- **Friction and restitution:** Bullet combines them by multiplying (stock Bullet; BulletSim's build
  unverified). Set `frictionCombineRule` and `restitutionCombineRule` to `R3_COMBINE_MULTIPLY` on every
  collider.
- **Damping:** Bullet scales velocity by (1 − d)^dt, and Rapier is believed to use 1 / (1 + dt·d) (both
  unverified). Convert the coefficients so vehicle tuning (`BSDynamics`) keeps its feel.
- **Forces:** Rapier keeps forces until they are reset (`r3RigidBody_AddForce`: "it persists until reset").
  Bullet clears them after each `stepSimulation`. PhysicsStep resets the bodies it pushed.
- **Linear and angular factors:** only 0 and 1 are used by default. Avatars use 0; vehicles default to
  `<1,1,1>` (`BSParam.cs:699-702`). Those map to axis locks. Fractional factors set in the configuration are a
  gap, logged once.
- **Anisotropic friction:** never called, and a gap.

### H12. Interop and threading (input to Phase 1.3)

- **Structs are blittable.**
  - `R3Vector` is three floats and `R3Rotation` is x, y, z, w.
  - `R3Bool` is uint32, so it must not be marshalled as a C# bool.
  - Handles are 16-byte values `{world*, index, generation}`. A removed or stale handle fails with
    `R3_INVALID_HANDLE` instead of crashing, which is an improvement on Bullet's raw pointers.
  - The official C# example (`bindings/c/examples/RapierNative.cs`) uses DllImport, Cdecl, and `r3CheckAbi`
    + `r3PodLayout` at start-up to catch layout mismatches.
  - Mapping OpenMetaverse's `Vector3`/`Quaternion` straight onto these structs is unverified; copying field by
    field is safe.
- **Errors** come back as R3Status plus `r3LastStatus` / `r3LastError`. The error handler is per thread
  (`r3SetErrorHandler`).
- **Threading:**
  - BulletS calls the engine from the physics thread: taints run in `ProcessTaints` around the step.
    `RayTest2` runs under `PhysicsEngineLock` (`BSScene.cs:1081`) or in a taint. Rapier needs the same
    discipline: `r3FreeWorld` requires that no other thread is calling, and `r3SetNumThreads` must not race a
    step.
  - Rapier's own parallelism is inside `r3Step` (parallel build + `r3SetNumThreads`). With one region per
    process there is one world per process.

## 4. Verdict

**The `BSAPITemplate` route is viable for the prototype, and it is the cheaper one.**

- Every call BulletS makes has a direct Rapier call or a straightforward emulation. The only two gaps it hits
  are sleep-tuning knobs.
- Linksets, vehicles (`BSDynamics`), avatar movement, axis locks, hover, move-to-target, materials and terrain
  management all stay as they are in BulletS's C#.

**Size of the shim:**

- **One new file, `BSAPIRapier.cs`**, about **2,500 to 3,500 lines of C#**:
  - DllImport declarations for roughly 130 `r3*` functions;
  - about 25 blittable structs;
  - wrapper classes for world, body, shape and constraint;
  - the 184 overrides;
  - about 300 lines of step, update and collision gathering;
  - about 400 lines of shape, compound and heightfield handling.

  That is the same order as `BSAPIXNA.cs` (2,603 lines) and `BSAPIUnman.cs` (2,155).
- **One more change outside the template:** a `case "rapier"` in `BSScene.SelectUnderlyingBulletEngine`
  (`BSScene.cs:440-474`).
- **P/Invoke straight into `rapier.h` is enough.** The C API already has the bulk calls the step needs
  (`r3ActiveRigidBodies`, `r3RigidBodyReadStates`, `r3Collider_ContactPairs`, `r3IntersectionPairs`).
  Dimforge ships a C# P/Invoke example, and handles are safe values.
- **No Rust shim to start.** A small one (a few hundred lines) becomes worth it only if Phase 3 profiling shows
  the per-collider collision calls (H2) or the per-call taint traffic costing real time. That is Phase 1.3's
  decision.

**What would make me pick a from-scratch module instead:**

1. **BulletS's behaviour is what residents object to.** The backend inherits BulletS's C# behaviour: avatar
   motor and stairs, vehicle code, linkset handling, all tuned against Bullet. If Phase 0.4 or the Phase 4 side
   by side shows those are what residents dislike compared with ubODE, Rapier underneath won't fix it. A
   ubOde-style module, with ubOde's C# logic over Rapier, would then be the route.
2. **BulletS's own C# is the bottleneck.** If Phase 3 profiling shows that taint processing, per-object
   `UpdateProperties` and `BSDynamics` dominate a busy frame rather than the solver, BulletS's C# caps the
   speed-up whatever engine is underneath.
3. **Rapier's character controller turns out to be needed for avatars.** That is still possible inside BulletS
   as a new actor (H10), so it is not a reason on its own.

None of these is visible from a desk check. Each is a Phase 0 / 3 / 4 measurement.
