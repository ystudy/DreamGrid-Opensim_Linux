# Where the time goes: Rapier inside OpenSim (BulletS + BSAPIRapier)

Date: 2026-11-06. Build measured: worktree at `af52b49f` (the Task 13 build, BulletS code identical to `58c75be7`) plus
bench-only timers. Line numbers are for `af52b49f`; where the branch head (`eebfd621`) moved a line it is given too.
Nothing was committed. The timer patch is in `perf-timers.diff (bench-only, kept out of the repo)` next to this file.

## Short answer

Rapier in OpenSim is slower than the standalone bench for four reasons, in this order of size:

1. **The pile never goes to sleep.** It is a scene/tuning effect, not a wake-up bug. pile-500 keeps 412 of 500 bodies
   awake, so `r3Step` costs 6.9 ms. Standalone keeps 49 awake and costs 0.95 ms. The cause is friction: prim 0.6 ×
   terrain 0.3 (BulletS multiplies them) gives 0.18 on the bench's sloped terrain, so the pile keeps sliding. With
   `TerrainFriction=1.0` (0.6 combined, the standalone value), 9 bodies stay awake, `r3Step` drops to 1.0 ms and the
   frame drops from 12.0 to 6.2 ms.
2. **Collision gathering costs 3.9–4.3 ms per frame in busy scenes.** That is 34% of pile-500 and 15% of kick-1000.
   OpenSim subscribes every physical prim to collisions, because the default collision sound needs them. The backend
   then calls `r3Collider_ContactPairs` once per subscribed collider per substep: 2,730 calls returning 27,800 pairs
   per frame in pile-500, and 5,460 calls returning 10,500 pairs in kick-1000. Each pair is seen twice. The cost stays
   when the pile sleeps: 4.3 of the 6.2 ms.
3. **There are more substeps.** BulletS steps 1/60 s (5.46 steps per frame) where ubODE and the standalone bench step
   0.02 s (4.55 per frame). On kick-1000, `FixedTimeStep=0.02` saves 3.3 ms (26.5 → 23.2 ms mean).
4. **Rapier itself is slower per body-step** than standalone: 4.4 µs against 3.0 µs on kick-1000, after allowing for
   the substeps. Part of that is measured:
   - the heightfield internal-edge fix costs 1.8 ms on kick-1000 and 0.2 ms on kick-100 and npcs-50;
   - the `parallel` build running on one thread costs 6–8% (measured standalone).

   The rest is probably the scene (sloped terrain, cylinders as convex hulls, more sliding) and isn't proven.

**OpenSim's own C# work is small:** 0.1–1.4 ms per frame (taints, pre/post-step, collision dispatch, UpdateProperties,
terse updates). That is the same order as ubODE's 0.1–1.3 ms.

**P/Invoke count is not the problem.** There are 530–7,500 native calls per frame. ubODE makes more: an estimated
~16,000 for pile-500. The cost is in what the gather calls do: per-collider pair walks and big buffer copies.

**The waits don't matter.** The never-sleep wake-up costs 0.002 ms, and taints and pre-step cost ≤ 0.05 ms.

**The biggest single win is not an overhead: run Rapier on 2 threads.** The default is 1 (`RapierNumThreads`). With 2,
kick-1000 goes from 26.5 to 17.8 ms on this 2-vCPU VM, and process CPU rises only from 28.9% to 32.2%.

**A correctness bug turned up on the way.** BulletS's own terrain height lookup is wrong on slopes:
- the mean error is 0.30 m and the worst is 20 m;
- because of it, `PositionSanityCheck` teleports resting prims upward 1–10 times per frame;
- it costs almost no time, but it changes behaviour.

  - Per-function native call counts per window went to `bstime-<tag>.csv.calls`.

- **Timer overhead is negligible.** kick-1000 measured 26.52 ms p50 with timers, against 26.48 in Task 13.
  - The sections add up to the frame logger within 0.25 ms. The rest is the scene's physics sync, outside `Simulate`.
  - pile-500 read 12.2 ms against Task 13's 10.9 ms. Two repeats agreed (12.24 and 12.29), so I put the gap down to
    pile-state variance between runs.

    needed in the end.
  - `[BulletSim]` ini values: `FixedTimeStep`, `RapierNumThreads` and `TerrainFriction`.
  - A one-off terrain check: ray casts against BulletS's height lookup, logged as `[BENCH TERRAIN]`.
- **Two runs were contaminated, and both were re-run clean.** The bench leaves the NPCs of an `npcs-*` run alive when
  the next run loads its OAR, so the first `kick-1000-fts02` and `kick-100-hfnofix` runs carried 50 extra avatars. The
  clean re-runs are the `perf3-*` tags. Every other run had the expected object count (`physobjects` counter).
- **Raw data:**
  - `/root/bench/perf-20261106/`: `bstime-*`, `frames-perf*`, `perf-results.csv`, the queue logs and the scripts.
  - `physics-results.csv` was left untouched.

## Frame flow: BulletS + Rapier against ubODE

**BulletS + BSAPIRapier**, all on the heartbeat thread with `UseSeparatePhysicsThread=false`, once per OpenSim frame
(about 91 ms):

1. `ProcessTaints` runs the changes queued by the scene and scripts: impulses, position sets, shapes.
2. `TriggerPreStepEvent` runs the actors: avatar mover, vehicles (`BSDynamics.Step`), hover and so on. It runs once
   per frame, not per substep.
3. `ProcessTaints` runs again.
4. `PE.PhysicsStep` (`BSAPIRapier.Step.cs:43`):
   1. `PlanSteps` takes whole 1/60 s steps from an accumulator: 5.46 per frame, at most 10.
   2. The never-sleep bodies (avatars) are woken.
   3. Per substep: `r3Step`, then `GatherCollisions`, then `BreakOverstrainedJoints`. `GatherCollisions` walks every
      collider in `WantsCollisions`, calls `r3Collider_ContactPairs` on it, and for each new pair with an active
      contact calls `r3ContactPoints` and `r3Collider_Position`.
   4. `ResetAppliedForces`.
   5. `GatherUpdates`: `r3ActiveRigidBodies` and `r3RigidBodyReadStates`, in bulk, once per frame. The results are
      filtered against BulletSim's tolerances, then the moving-sent, forced and pending sets are added.
5. `TriggerPostStepEvent` and `ProcessTaints` run.
6. Collision dispatch: `SendCollision` both ways for each recorded pair. That calls `BSPhysObject.Collide`, which
   allocates and lists the object in `ObjectsWithCollisions`.
7. `UpdateProperties` runs for each reported body. It calls `PositionSanityCheck`, which does a terrain lookup and,
   if the body seems underground, moves it up and zeroes its motion. Then `PostUpdate`.
8. `SendUpdatesToSimulator`:
   - `SendCollisions` per colliding object, throttled to 50 ms, and for every avatar;
   - `RequestPhysicsterseUpdate` per updated object.

**ubODE** (`ODEScene.Simulate`, `ODEScene.cs:1614`):

1. Its changes queue (`DoAChange`) runs once per frame.
2. Then, per **0.02 s** step (4.55 per frame):
   1. `Move()` for every character and every active prim, so the controllers run per substep.
   2. Queued ray casts.
   3. `collision_optimized`: ODE's space collide plus the C# near-callback. Contact joints are built and collision
      events accounted inline (`Collision_accounting_events`, `ODEScene.cs:1013`), so collision reporting costs no
      separate query.
   4. `SendCollisions` for prims that have events.
   5. `WorldQuickStep`.
   6. `UpdatePositionAndVelocity` for every active prim. This is about 3–5 native reads each (`BodyIsEnabled`,
      `GeomGetPosition`, `GeomGetQuaternion` and the two velocities), with its own movement thresholds, and calls
      `RequestPhysicsterseUpdate` directly.
3. Bodies auto-disable (ODE's own sleep), but its prim thresholds are strict, so piles stay awake.
4. ubODE stops out-of-bounds prims itself, before OpenSim's border code sees them.

**What differs:**

| | BulletS + Rapier | ubODE |
|---|---|---|
| Steps per frame | 1/60 s: 5.46 | 0.02 s: 4.55 |
| Controllers (avatar, vehicle) | once per frame, before the steps | per substep |
| Collision reports | queried after each substep, per subscribed collider, from the narrow phase | produced while the contacts are made |
| Which bodies are read | the awake set, in bulk, once per frame | every active prim, per substep, one call per field |
| Native calls per frame (pile-500) | 5,700 | about 16,000 (estimated: 7 calls × 500 prims × 4.55 steps, plus contacts) |
| Sleep | Rapier islands: 0.4 m/s and 0.5 rad/s for 2 s; prims can sleep, avatars are woken every step | auto-disable, strict thresholds; piles never sleep |
| Under-terrain check | every reported update (`BSPrim.cs:368`), with a broken lookup | none per update |

Per object, the pattern is as follows.

**Every physical prim pays this, whatever it does:** one `r3Collider_ContactPairs` per substep, because every physical
prim subscribes to collisions. OpenSim's `SceneObjectPart.UpdatePhysicsSubscribedEvents` subscribes any physical prim
with the default collision sound (`SceneObjectPart.cs:5161`, `hassound`).

**Per collision pair reported:**
- 2 native calls, once per frame;
- 2 `Collide()` calls in C#.

**Only the bodies that change pay** the per-body costs: an impulse is 4–5 calls (`AddForce`/`AddTorque`, `BodyType`,
`WakeUp`, reset) and a position set is 4. Reading updates is 3 bulk calls per frame however many bodies move.

| 1 | BulletS per-frame work (taints, pre/post-step actions, UpdateProperties, collision callbacks) | **refuted as the main cause** | C# outside the native step and gather is 0.12–1.35 ms per frame (4–8%). The largest part is collision dispatch: 0.49–0.72 ms, plus 0.16–0.30 ms for SendCollisions. Taints ≤ 0.03 ms, pre-step ≤ 0.03 ms, UpdateProperties ≤ 0.25 ms. |
| 2 | P/Invoke call count per object per step | **refuted as a count, confirmed for the gather calls** | 530–7,500 calls per frame, against ubODE's ~16,000 for pile-500. The rest of `r3Step` has no proven cause. It is about 4.05 µs per body-step on kick-1000 without the internal-edge
fix, against 3.0 µs standalone (about 3.8 µs after the parallel-build cost). Likely causes:
- the sloped terrain (more sliding contacts);
- cylinders as convex hulls of the Meshmerizer mesh (`ShouldUseSingleConvexHullForPrims`, `BSAPIRapier.Shapes.cs:412`)
  where the standalone bench uses a primitive cylinder;
- a fixed cost of about 0.1 ms per step (from a fit of kick-100 against kick-1000).

## Ranked fixes

The gains are measured where a test exists, otherwise estimated (marked "est."). They overlap, so they don't simply
add up. Rough combined estimate:
- kick-1000: 26.5 ms → ~12–14 ms, under the Decision 3 limit of 15 ms;
- pile-500: 12.2 → ~3 ms.

| Rank | Fix | Where | Expected gain | Risk |
|---|---|---|---|---|
| 1 | **Run Rapier on 2 threads by default when there are at least 2 cores.** Ideally make it a launcher setting, scaled by the number of region processes on the host. | `BSParam.cs:854–855` (`RapierNumThreads`, default 1); applied at `BSAPIRapier.cs:498` | kick-1000 −8.8 ms (−33%), measured. Bigger with more cores. | Medium. DreamGrid runs several region processes per host, so per-process pools could oversubscribe the cores. Rayon workers spin briefly, which takes CPU from scripts. Results can vary run to run with thread count, so check determinism expectations. |
| 2 | **Gather collisions once per frame, not per substep and per collider.** Read pairs after the last substep with one world-level `r3ContactPairs` call, so each pair is seen once. Skip pairs where neither side wants events, and skip unchanged sleeping pairs. Use Rapier collision-start events (`r3Collider_SetActiveEvents` and `r3EventCollector`) to catch touches that begin and end inside a frame. A small Rust bulk call that returns only the reportable pairs with their deepest point would do better still. | `BSAPIRapier.Step.cs:61–68` (substep loop) and `:115–141` (`GatherCollisions`); branch head `:81` and `:169` | 3.9–4.3 ms → est. 0.5–0.9 ms. | 3 | **Let piles settle: raise prim-terrain friction for Rapier,** for example `TerrainFriction` 0.6–1.0, or a Max/Average combine rule for terrain colliders only. | `BSParam.cs:612` (`TerrainFriction` 0.3) or the combine rule at `BSAPIRapier.Bodies.cs:76–77` / terrain colliders in `BSAPIRapier.Terrain.cs` | pile-500 −5.8 ms (12.0 → 6.2), measured. cutting P/Invoke count for its own sake.

## Also seen

- **Out-of-bounds stops.** kick and cars still log "went out of bounds … Stopping": 164 per kick-1000 run in Task 13,
  and the same pattern here. ubODE handles region edges itself (`ODEPrim.UpdatePositionAndVelocity`, `m_outbounds`),
  and BulletS leaves it to OpenSim's border code. It isn't a cost, but it is a behaviour difference.
- **The bench `settle()` wait.** `bench.py` waits up to 10 minutes for CPU below 10%, so busy scenes are measured
  about 11 minutes after load. Light scenes are measured 1–2 minutes after. Keep that in mind when comparing windows.
